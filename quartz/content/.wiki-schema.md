# Wiki Schema

> 这个文件是所有 wiki 页面的质量契约。任何 Agent ingest 素材时，必须按此 schema 产出页面。你和 AI 可以一起调整它。

## 知识库信息

- 主题：个人知识库
- 语言：中文
- 创建日期：2026-05-05
- 更新日期：2026-05-24
- 版本：2.0

## 目录结构

```
kb/
├── .wiki-schema.md      # 本文件（配置规范）
├── index.md             # 内容索引（目录）
├── log.md               # 操作日志（时间线）
├── raw/                 # 原始素材（只读，不可修改）
├── wiki/
│   ├── overview.md      # 快速导航 + 统计
│   ├── entities/        # 实体页（工具、模型、人物、概念）
│   ├── topics/          # 主题页（知识领域、方法论）
│   ├── projects/        # 项目跟踪（会议纪要、进展、决策、里程碑）
│   ├── sources/         # 素材摘要（每个素材一篇摘要）
│   ├── comparisons/     # 对比分析
│   └── synthesis/       # 综合分析
```

## 页面命名规范

**核心铁律：`[[链接名]]` 必须与文件名（去 .md 后缀）完全一致。违反此规则会产生断链。**

- 实体页：`wiki/entities/{名称}.md`，用小写+连字符
  - 例：`claude-code.md`、`deepseek-v3.md`、`mcp-protocol.md`
- 主题页：`wiki/topics/{概念名}.md`
  - 例：`agent-memory-approaches.md`、`prompt-engineering.md`
- 素材摘要：`wiki/sources/{来源}-{短标题}.md`
  - 例：`karpathy-llm-wiki.md`
  - 短标题用中划线 `-` 连接单词，日期写在 frontmatter 的 `created` 字段
- 对比分析：`wiki/comparisons/{A}-vs-{B}.md`
  - 例：`claude-code-vs-cursor.md`
- 综合分析：`wiki/synthesis/{主题}-综合.md`
  - 例：`coding-agent-综合.md`

**命名一致性检查清单**（每次创建文件时必须遵守）：
1. 确定文件名 → 所有 wikilink 链接 必须与此文件名一致
2. 不要在链接中使用文件名中没有的空格、标点
3. 同一个概念在所有文件中只能有一种链接写法

**标题语言规范**（每次创建/更新页面时必须遵守）：
- **主标题使用中文**：`# 中文标题`，让浏览时一眼看懂
- **副标题使用英文**：`> English subtitle — brief description`，保留原始名称可检索性
- 文件名（用于 wikilink 链接）保持英文 kebab-case，不因标题语言改变
- 示例：
  ```markdown
  # CPA 订阅转 API 代理工具

  > CLI Proxy API — 将 GPT Plus 订阅额度转为标准 OpenAI API
  ```

## 实体页 vs 主题页 区分规则

**实体页（entities/）** 回答"它是什么"：
- 用于：具体工具、具体模型、具体人物/组织、具体概念
- 例：Claude Code、DeepSeek-V3、Cursor、RAG、MCP
- 核心结构：定义 → 技术参数 → 详细内容 → 从各素材中综合的观点

**主题页（topics/）** 回答"关于这个领域的知识体系"：
- 用于：研究主题、学习路径、知识领域、行业动态
- 例：Agent Memory Approaches、AI 编程工具、Prompt Engineering
- 核心结构：核心观点 → 素材汇总表 → 子主题划分 → 关键概念链接

**判断规则**：
- 如果是"一个具体的东西" → 实体页
- 如果是"一个知识领域/学习方向/研究话题" → 主题页
- **同一个名字不能同时出现在 entities/ 和 topics/ 下** — 如果已有实体页，主题页应改名

## 置信度标签

| 标签 | 含义 | 何时使用 |
|---|---|---|
| `[confirmed]` | 广泛共识、有权威来源支撑 | 论文结论、官方文档、行业基准 |
| `[emerging]` | 新趋势、社区在讨论但未定论 | 新技术发布、社区热议方向 |
| `[opinion]` | 个人或特定作者的观点 | 博客文章、推特 thread、播客观点 |
| `[hypothesis]` | 你自己的推测或猜想 | 从多篇素材中推导出的个人结论 |

## 内容分级处理规则

根据素材长度和信息密度自动分级：

**完整处理**（素材 > 1000 字）：
1. 每个新素材**必须**生成摘要页（`wiki/sources/` 下）
2. 从素材中提取 3-5 个关键概念
3. 检查是否需要创建新的实体页
4. 检查是否需要创建或更新主题页
5. 更新 `index.md`
6. 更新 `log.md`
7. 更新 `wiki/overview.md`

**简化处理**（素材 <= 1000 字，如短推文、小红书笔记）：
1. 生成摘要页（`wiki/sources/` 下）
2. 提取 1-3 个关键概念
3. 如果关键概念已有实体页，追加信息；如果没有，用纯文本标注（**禁止创建悬空链接**——不链接到不存在的页面）
4. 更新 `index.md` 和 `log.md`
5. 跳过主题页和 overview 更新

## 自动触发综合生成

当同一主题下素材数量达到阈值时，AI 必须自动触发生成：

- **comparisons 页面**：同主题下有 3 个以上可直接对比的实体 → 自动生成对比分析页
- **synthesis 页面**：同主题下有 5 篇以上素材 → 自动生成综合分析页（跨素材趋势、知识体系）
- 素材不足上述阈值但已达 3 篇 → 在主题页的"综合分析"节加强交叉视角分析

## 页面类型规范

### 1. Entity — 实体页

描述一个具体的模型、工具、框架、公司、人物。

**写作原则**：不要填模板。目标是让读者看完能理解这个实体是什么、为什么重要、跟同类有什么不同、自己能不能用上。

**深度自审清单**（写完后逐条过，答不上来就继续写）：
- 读者看完能做什么决策或行动？（如果不能 → 没写够）
- 素材中的具体数据、案例、观点都引用了吗？（如果漏了 → 补充）
- 这个实体跟同类工具/概念有什么不同？（如果没讲 → 缺关键信息）
- 留下"为什么"而不仅仅是"是什么"了吗？
- 工具类实体：安装方式、基本用法、适用场景都写了吗？
- 概念类实体：精确定义 + 与相似概念的区分清楚吗？
- sources 字段是否已回填所有关联素材？
- 正文（不含 frontmatter 和"相关"节）不低于 1500 字符（lint 脚本会在最后验证）

**模板：**
```markdown
---
type: entity
confidence: [confirmed|emerging|opinion|hypothesis]
created: YYYY-MM-DD
updated: YYYY-MM-DD
tags: []
sources: [关联素材文件名列表]
---

# [中文名称]

> [English Name] — [20 字以内概括]

## 核心特性
- [关键事实 1]
- [关键事实 2]
- [关键事实 3]

## 为什么重要
[2-5 句话说明这个实体在 AI 领域的位置和影响]

## 主要应用场景
[2-4 个场景，各有具体描述]

## 不同素材中的观点
### 关于 [主题A]
来源：[[素材摘要页]]
> "原文观点引用..."

## 实用信息（工具/模型类必填）
- 获取方式：
- 基本用法：
- 适用场景：

## 来源
[URL 或 raw/{hash}]

## 相关
- [[相关实体]]
- [[相关主题]]
```

### 2. Topic — 主题页

描述一个概念、方法论、技术方向、学习路径。

**写作原则**：主题页的本质是"关于这个领域，我已经知道了什么"。不止是罗列素材，而是形成自己的知识体系。

**深度自审清单**（写完后逐条过，答不上来就继续写）：
- 有没有基于素材形成自己的判断，而不只是转述？
- 不同素材之间的矛盾或互补关系分析了吗？
- 核心观点至少 5 条，每条有具体数据或案例支撑吗？
- 知识体系节：每个子方向有实质描述吗？（不只是列名字）
- 素材汇总表：每个素材独立链接到摘要页了吗？
- 有没有给读者一个清晰的"如果我想深入了解，从哪里开始"的路径？
- sources 字段是否已回填所有关联素材？

**模板：**
```markdown
---
type: topic
confidence: [confirmed|emerging|opinion|hypothesis]
created: YYYY-MM-DD
updated: YYYY-MM-DD
tags: []
sources: [关联素材文件名列表]
---

# [中文主题名]

> [English Topic Name] — [20 字以内概括]

## 核心观点
1. [观点一]（来源：[[素材A]]、[[素材B]]）
2. [观点二]（来源：[[素材C]]）
...

## 知识体系
### [子方向 1]
[2-3 句实质描述]

### [子方向 2]
[2-3 句实质描述]

## 素材汇总
| 素材 | 核心内容 | 关联实体 |
|------|---------|---------|
| [[素材A]] | ... | [[实体1]] |
| [[素材B]] | ... | [[实体2]] |

## 综合分析
### 不同素材的交叉视角
[对比异同]

### 趋势与判断
[基于素材的趋势判断]

### 未解决的问题
[列出或写（暂无）]

## 相关
- [[相关概念]]
- [[相关工具]]
- [[相关主题]]
```

### 3. Project — 项目跟踪

记录一个在进行的项目——不是"它是什么"（那是实体），而是"它现在怎么样了"。

**写作原则**：项目页是活文档。它记录目标、进展、决策、会议。不同于实体页的"一次性描述"，项目页会随着项目推进不断更新。

**深度自审清单**（写完后逐条过）：
- 项目目标和当前状态写清楚了吗？（读者能理解这个项目要做什么、做到哪了）
- 会议纪要都链接了吗？（每个相关 meeting note 都能从项目页找到）
- 关键决策记录了吗？（日期 + 决策内容 + 为什么这样决定）
- 关联了哪些知识领域？（项目涉及的技术/方法论链接到对应 topic）
- 里程碑明确吗？（哪些做完了、哪些待做）

**模板：**
```markdown
---
type: project
status: [active|paused|completed]
created: YYYY-MM-DD
updated: YYYY-MM-DD
tags: []
---

# [项目中文名]

> [English Name] — [一句话描述]

## 项目目标
[要达成什么，2-3 句话]

## 当前状态
[进行到哪了，最近在做什么]

## 会议记录
- [[会议纪要1]]
- [[会议纪要2]]

## 关键决策
| 日期 | 决策 | 原因 |
|---|---|---|
| YYYY-MM-DD | [决策内容] | [为什么] |

## 关联知识
- [[相关主题]]
- [[相关实体]]

## 里程碑
- [x] [已完成]
- [ ] [待做]

## 相关
- [[相关项目]]
- [[相关主题]]
```

**命名规范**：`wiki/projects/{项目名}.md`，英文 kebab-case

### 4. Source — 素材摘要

你读过的一篇文章、一个视频、一篇论文的消化笔记。

**写作原则**：摘要的价值在于"以后不用重读原文"。核心观点要具体到能引用，实操内容要完整到能照做。"我的收获"是你自己的思考——这是 wiki 最值钱的部分。

**深度自审清单**（写完后逐条过，答不上来就继续写）：
- 核心观点够具体吗？每条有数据/案例/步骤/结论支撑吗？（不能只有"XX 很好"）
- 代码块、Prompt、配置、分步教程——原文的实操内容原样保留了吗？
- 至少 2 段原文精彩摘录，优先保留含关键数据和独特洞察的段落
- 信息保留率达到 40% 了吗？（概念骨架 + 关键数据 + 实操内容）
- "我的收获"是自己的思考吗？这个素材改变了你的什么认知？
- 关键概念只链接到已存在的实体页或本批同步创建的页面了吗？（禁止悬空链接）

**模板：**
```markdown
---
type: source
confidence: [confirmed|emerging|opinion|hypothesis]
created: YYYY-MM-DD
source_url: []
raw_files: []
tags: []
---

# [中文素材标题]

> [English Title] — [20 字以内概括]

## 核心观点
- [原文核心论点 1]（含具体数据/案例）
- [原文核心论点 2]（含具体数据/案例）
- [原文核心论点 3]（含具体数据/案例）

## 实操内容保留
### 代码/配置
[原样保留，无则写（本文无实操代码/模板/步骤）]

### Prompt 模板
[原样保留]

### 操作步骤
[关键步骤保留]

## 我的收获
[你从这个素材中学到了什么新东西？改变了什么认知？]

## 原文精彩摘录
> [摘录 1 — 优先含关键数据和案例的段落]

> [摘录 2 — 优先含独特洞察的段落]

## 值得引用吗
[值得 / 一般 / 不值得，理由一句话]

## 相关
- [[相关实体]]
- [[相关主题]]
```

### 5. Comparison — 对比分析

两个或多个实体/方案的对比。

**写作原则**：读者看对比是为了做选择。对比维度必须是实际决策中会考虑的点，不是表面参数。结论要明确到"什么情况下选哪个"。

**深度自审清单**（写完后逐条过，答不上来就继续写）：
- 对比维度是实际决策中会考虑的点吗？（不是表面参数堆砌）
- 每个对比格有实质内容吗？（不能留空）
- 场景建议具体吗？（不能是"按需选择"，要给出清晰条件）
- 结论明确吗？读者看完知道该选谁吗？

**模板：**
```markdown
---
type: comparison
confidence: [confirmed|opinion|hypothesis]
created: YYYY-MM-DD
updated: YYYY-MM-DD
tags: []
---

# [A] vs [B]：[对比维度]

> [A] vs [B] — [一句话结论：选哪个，在什么场景下]

## 对比表
| 维度 | [A] | [B] |
|---|---|---|
| [维度1] | ... | ... |
| [维度2] | ... | ... |

## 场景建议
- 如果 [条件] → 选 [A]
- 如果 [条件] → 选 [B]

## 相关
- [[A]]
- [[B]]
```

### 6. Synthesis — 综合分析

对多个 source/entity/topic 的交叉分析、趋势判断、个人结论。

**写作原则**：synthesis 的价值在于"从多篇素材中看到别人没看到的模式"。不是汇总，是推断。永远标注为 `[hypothesis]` 或 `[opinion]`——这是你的个人判断，不是事实。

**深度自审清单**（写完后逐条过，答不上来就继续写）：
- 多个素材之间发现了什么共同模式或矛盾？
- 你的推断是基于哪些具体素材？（"触发素材"必须全部链接）
- 这个推断还需要什么证据来验证？（"后续要追踪"不能空）
- confidence 标签是 `[hypothesis]` 或 `[opinion]` 吗？（不能标 confirmed）

**模板：**
```markdown
---
type: synthesis
confidence: [hypothesis|opinion]
created: YYYY-MM-DD
tags: []
---

# [主题]：我的综合分析

> [English Topic] Synthesis — [20 字概括]

## 触发素材
- [[source A]]
- [[source B]]

## 它们有什么共同点
[从多个素材中发现的模式]

## 我的推断
[基于这些素材的个人结论]

## 后续要追踪的
[这个推断需要什么证据来验证？]

## 相关
- [[相关主题]]
- [[相关实体]]
```

## frontmatter 的 sources 字段

实体页和主题页的 `sources: []` 字段**必须回填**关联素材列表：
- 每次 ingest 更新实体页时，将新素材的文件名追加到 sources 列表
- 格式：`sources: [2026-04-28-素材标题1, 2026-04-28-素材标题2]`
- 此字段用于追踪"哪些素材贡献了这个页面的信息"

---

## 交叉引用规范

- 页面间使用 `[[页面名]]` 语法（Obsidian 兼容的双向链接）
- `[[页面名]]` 中的"页面名"必须与目标文件名（去 .md）完全一致
- 素材引用格式：`来源：[[素材摘要页]]`
- 每个页面底部维护"相关"小节，至少一个链接
- **禁止创建悬空链接**：在写入双向链接之前，必须先确认对应的 .md 文件已存在或将同步创建。未创建的实体用纯文本标注，不要创建指向不存在页面的链接

---

## 通用质量禁止项

**这些内容不要出现在 wiki 里：**
- 长段引用原文（放 raw/ 里去，wiki 只放消化过的）
- 模糊的"值得关注"而没有说为什么
- 没有上下文的链接（每个 wikilink 链接 要在上下文中说清楚它和本页的关系）
- "可能"、"或许"、"值得思考"等无信息量的词
- 占位文本："待补充"、"待完善"、"暂无"

---

## Schema 的进化

这个 schema 本身会随着使用而演进。如果你发现：
- 某种类型的页面总是写不好 → 调整该类型的模板
- 需要新的页面类型 → 在这里新增
- 某些规则在阻碍而非帮助 → 修改或删除

Schema 是工具，不是教条。修改 schema 时记得同时更新 git，这样旧的 wiki 页面可以追溯到当时的标准。
